# AIDEV-216 Review Attempt 3 Findings

## Summary

Independent Review attempt 3 confirmed that the prior five remediation findings were closed, then found a critical first-session process-allocation race. A fixed process lease could expire while runtime resolution or another pre-registration operation remained unresolved, allowing another owner to spawn a second process for the same run and role before exact-session registration rejected one contender.

R3-001 requires one fenced allocation protocol spanning runtime resolution, session lookup and validation, instruction loading, spawn, handshake, generation claim, and registration. Operations must be bounded, the lease renewed and verified around side effects, provisional first-session ownership persisted before spawn, and stale owners prevented from spawning or registering. Fake-clock races must cover every pre-registration stall and prove that at most one process/session allocation is created.

## Key Takeaways

- Lease acquisition alone is insufficient when setup can outlive the lease.
- A persisted `spawning`/`spawned` allocation must fail closed because an expired owner's external spawn outcome may be unknown.
- Generation claims and first-session registration require the same current fencing token as process creation.
