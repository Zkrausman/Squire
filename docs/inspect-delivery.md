# Passive delivery receipt inspection

Run `node bin/squire.mjs inspect-delivery project.json TICKET_ID` to inspect one ticket's retained delivery-evidence chain. The command reads only the project ID and absolute state directory from the supplied config. It does not validate or initialize runtime settings and runs before the CLI constructs a `Store`.

Inspection captures the existing SQLite database and optional WAL through the private-copy reader, selects one ticket from that snapshot, then closes and removes the copied database before reading receipt files. It follows only the selected ticket's retained reference and each receipt's `previous` reference. Every file is resolved through the hardened delivery-evidence reader. The fixed `projects/<projectId>` ancestors and receipt directories are checked for ordinary symlink or identity changes around traversal.

The JSON response is a bounded projection. It includes validated candidate hashes and generation, safe check labels, and selected fields from the seven known fact kinds: publication intent/observation, merge-candidate CI observation, selected required checks, merge intent/verification, and postmerge observations. Older candidate, generation, or policy records remain `historical`; earlier records for the same current fact slot are `superseded`. A selected check whose head cannot be tied to the candidate or a retained matching synthetic merge makes the chain incomplete. Actual failed checks, moved-base observations, mismatched merge-candidate trees/parents, and dirty or wrong-head postmerge observations remain visible as observations.

`status` is `resolved` only when the full retained chain passes reference, byte-integrity, identity, shape, and output checks. `incomplete` always returns an empty `facts` array after a corrupt link, malformed known fact, traversal limit, timeout, changed fixed directory, or output limit. Missing or legacy ticket anchors and unavailable project snapshots have `status: unavailable`. The fixed reason code is safe to record; raw reader errors and receipt content are never returned.

Limits are 128 references, 128 KiB per referenced file, 16 MiB total referenced bytes, 64 KiB serialized output, and a cooperative two-second traversal budget checked between and after reads. A stalled native file operation cannot be cancelled by this budget. The source database is never connected to SQLite; only ordinary read access to the database, WAL, and receipt files occurs. Access times can change. Database, WAL, and evidence bytes and their size, modification time, and change time remain unchanged during inspection. A failed inspection has no retries and makes no partial-success claim.

Every result labels `acceptance` as `not_evaluated`, `liveness` as `unknown`, and `remoteState` as `not_observed`. A resolved chain means that retained local references and bytes were readable and internally compatible with the projection rules. It does not authenticate a producer or establish current GitHub state, acceptance, delivery readiness, recovery authority, or permission to change controller state.
