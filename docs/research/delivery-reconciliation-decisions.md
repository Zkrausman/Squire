# Delivery interruption and postmerge decisions

This expands the existing [operations warning](../OPERATIONS.md) into a decision table; it does not add recovery capabilities or grant execution authority.

The question is whether a ticket has an unknown remote effect, a known exact merge awaiting verification, or a known failed delivered check. These states need different evidence. A recorded merge is not a shipped result; a passive resolved chain is not current remote state or permission to resume.

## Source-backed distinctions

| Retained or observed condition | Current source behavior | Decision boundary |
| --- | --- | --- |
| Merge request response was lost | [GitHub merge](../../src/delivery.mjs#L139-L158) rereads the PR after a request error; if merged, it verifies the returned merge. An unconfirmed response does not itself establish success. | Do not infer failed mutation from a transport error or repeat implementation on that basis. A future authorized reconciliation needs exact PR/head/base/tree/ancestry evidence and clear producer ownership. |
| PR is observed merged while re-entering publication/CI/merge | [Controller delivery phases](../../src/controller.mjs#L540-L553) reconcile an existing publication before rebasing. [Merge verification](../../src/delivery.mjs#L130-L137) checks SHA, exact tree and method-specific parents. Candidate verification/review gates precede that controller path. | Exact verified merge advances to postmerge verification; it is not ticket shipment or criterion acceptance. Missing local candidate/review evidence is not waived by remote merge state. |
| Local bare branch already equals the candidate | [Controller local-delivery branch](../../src/controller.mjs#L552-L553) enters postmerge at the candidate SHA. | This is the local route, not evidence that GitHub policy, CI or remote PR reconciliation passed. |
| Postmerge checks fail, checkout becomes dirty or head changes | [Postmerge phase](../../src/controller.mjs#L579-L590) materializes the recorded merge, checks its tree, runs setup/checks, records an observation, then refuses shipment on failed checks, dirty state or wrong head. | Preserve the merge and failing observations. Source code implements no rollback here. A blocked ticket with a merge SHA halts its repository lane; dependent tickets do not become eligible merely because the merge exists. |
| Existing delivered checkout is dirty or at another head | [mergeWorkspace](../../src/workspace.mjs#L272-L292) refuses that existing checkout as `merge_workspace_dirty`. It does not reset or discard it to make a retry pass. | Keep the checkout/evidence. Do not describe repeated checks as an automatic repair of changed bytes. Any cleanup or corrective change needs its own authorized scope. |
| Authoritative delivery/state persistence fails or producer remains unresolved | [Ticket error path](../../src/controller.mjs#L604-L605) propagates `storeTransactionFailed`, `producer_unresolved` and lifecycle `persistenceFailed`. [Delivery evidence](../../src/delivery-evidence.mjs#L59-L84) marks persistence failure; [producer closure](../../src/controller.mjs#L108-L125) requires a recorded normal outcome. [Store.resume](../../src/store.mjs#L895-L901) first requires clear producer scopes. | These unresolved producer outcomes remain fenced. Terminal process evidence, a merged PR or a supplied SHA cannot clear them. Optional [verification diagnostic retention](../../src/controller.mjs#L503-L508) can instead become unavailable without changing verification/repair/review behavior; that failure alone does not establish an unresolved producer. This guide supplies no import, settlement or replay authority. |
| Known blocked ticket is eligible for an explicitly authorized retry, with scopes clear | [Store.resume](../../src/store.mjs#L895-L925) preserves retry history/counters. A selected blocked/waiting ticket with `postmerge_failed` **or any merge SHA** returns to `postmerge`; one with a candidate head and no merge returns to `verifying`. Special recovery records have additional guards. | This describes state selection, not permission to invoke it. A postmerge retry runs setup and executable checks again under the normal gates; it is not a passive observation or a new implementation by definition. Current execution holds still prohibit such a retry. |
| Passive delivery inspection reports `resolved` | [Inspection contract](../inspect-delivery.md) validates the bounded retained chain and labels acceptance not evaluated, liveness unknown and remote state not observed. Failed check/postmerge observations can remain present in a resolved chain. | Internal reference integrity is not a passing result, actual current remote state, owner approval or scope release. An incomplete chain withholds facts rather than proving no merge occurred. |

## What closes this question

Retain the current separation: remote mutation reconciliation establishes which exact merge occurred; postmerge verification establishes the delivered tree/check result; version-2 criterion resolution establishes the supported criterion proof; clear producer ownership remains a prerequisite throughout. Project-wide integrated acceptance is a later, separate completion gate.

The existing [lost-local-merge fixture](../../test/controller.test.mjs#L136-L144), [postmerge-failure fixture](../../test/controller.test.mjs#L166-L174) and [GitHub lost-response matrix](../../test/delivery-evidence-matrix.test.mjs#L135-L164) are relevant **test source**, not new execution results.
