# SQF04 authority evidence and anchor/worker split

Prepared 16 October 2026 against Squire `288e75b415bc08f77b9409b4ac2291b602de7405`. **Design only; no implementation or runtime admission.** This completes the bounded source-contract preparation, not the native containment prerequisite. It does not authorize installations, identities, privileges, policies, processes, fixtures, provider calls or publication.

## Decision and supported conclusion

Retain the selected trusted system-manager transient service on a nondelegated cgroup-v2 domain, an outside observer, and a retained in-boundary trusted supervisor anchor. Do not reopen provider selection. The existing private design has SHA-256 `46a69d0d60a29b5c85ba774a23ce19c5e17649a0c223fb2036c83b86f8626a1c`, exactly the `SQF04_DESIGN_SHA256` source constant. Its frozen anchor-only snapshot and later teardown remain required.

The missing mechanism is **an authenticated authority producer and an enforceable observer/anchor/worker split**. The existing implementation supplies neither. Its authority hashes and identity strings are assertions supplied to non-admitting comparators. Source inspection therefore supports **required authority route not provided by the current Squire adapter**. This is not a finding that the host lacks every possible mechanism: host policy, running manager and permissions were not inspected.

Use a protected controller/observer principal, a protected anchor principal, and a less privileged payload principal. Require a separately reviewed, already supported credential transition before payload exec; no new privileged launcher is selected or authorized here. Distinct UID numbers alone are insufficient: groups, capabilities, namespaces, IPC, writable code/receipts and broker access must preserve the split. A unit-wide `User=` setting does not itself give its anchor and child different authority. Same-UID operation requires an independently established equivalent boundary; the current default cannot be presumed equivalent.

If no existing supported mechanism satisfies this contract, close that route as unsupported and retain the fence. Choosing or provisioning a new privileged mechanism is a separate owner decision. A pure companion parser/comparator can be implemented independently after admission, but would not supply the missing mechanism and is not a prerequisite worth shipping merely to fill queue capacity.

## Proposed companion interface

Use a separately versioned companion, not a change to historical v1 settlement hashes or the old seven digest meanings. It is a specification; no schema implementation is supplied.

Strict JSON object, unknown keys rejected, maximum 128 KiB UTF-8, nesting at most 16, collections at most 100 entries, no duplicate IDs, finite safe integers only. Text identifiers are bounded to 160 characters, opaque OS references to 2048; SHA-256 is lowercase 64 hex. Do not serialize raw credentials, rules, inherited environment, argv, diagnostics or host paths into exported/public examples. Actual private authority records require their own protected retention policy.

Required top-level fields:

- `version: 1`, `kind: "sqf04_authority_evidence"`, `contractDigest`, `recordId` and `precedingRecordDigest`. `contractDigest` identifies the separately frozen companion specification/schema; it is not a self-hash. Compute `recordDigest` externally over the complete canonical JSON record, excluding only the detached authenticity envelope (which is not a record field). `precedingRecordDigest` is null for pre-exec and the exact predecessor recordDigest for snapshot/teardown. No self-referential digest field is serialized.
- `binding`: project, ticket, job, positive generation, operationId, requestDigest, admittedHeadSha, candidateSha, policyDigest, producerScopeId and scopeSealDigest. `admittedHeadSha` is the 40-hex controller-admitted workspace source head before this physical launch, fixed through the chain. `candidateSha` is null at pre-exec; at snapshot/teardown it is the 40-hex later controller-owned checkpoint candidate for this selected candidate-recovery route, independently obtained through the existing durable checkpoint comparison. Do not relabel the pre-launch head as that later candidate. The core operation/source/policy binding is invariant; only the explicitly phase-dependent candidate and seal move from null to independently bound values, then remain equal. Digest the canonical complete object, preserving policy array order; never rebuild expected binding from the incoming record.
- `producer`: issuerId, implementationDigest, trustRegistryRevision and keyOrChannelId. These are selectors into an independently configured trusted registry, never new trust anchors supplied by the record.
- `boundary`: bootId, managerEndpointId, unitName, invocationId, cgroupObjectId, anchorBirthId, observerBirthId and payloadPrincipalId. IDs must match observer-held identities; pathname equality is insufficient.
- `authorityReferences`: exactly the seven existing named digests above. Each resolves only through the trusted private producer/store, with exact bytes, kind, binding and immutable retention. References are not arbitrary paths or URLs.
- `split`: observerPrincipalId, anchorPrincipalId, workerPrincipalId, mechanismId, mechanismVersion, credentialTransitionDigest, peerProtectionDigest and handlePolicyDigest. A declared mechanism must already be allowlisted by trusted admission; a record cannot invent it.
- `validity`: bootId, issuedAtMonoMs, notBeforeMonoMs, expiresAtMonoMs, and revocationEpoch. All times use the same boot-bound monotonic source and safe nonnegative integer milliseconds. Include an authenticated issuance sequence/challenge reference in `recordId`'s private producer record.
- `phase`: one of `pre_exec`, `snapshot`, `teardown`. Each phase has its own immutable record and binding; later records reference the preceding record digest. An inventory seal is a settlement-time dependency: pre-exec uses an explicit `scopeSealDigest: null`, while snapshot/teardown require the existing durable seal. No pre-exec claim may pretend an inventory is already complete.

The detached authenticity envelope is **outside** these JSON claims. The trusted consumer selects a preconfigured authenticated local channel or verifier from the registry. It binds exact canonical content bytes, issuer, record kind, purpose, challenge, operation and registry revision. Self-supplied signatures, a boolean `authenticated`, a hash, UID text or a caller-created verifier result are never authentication. Cryptographic choice/key provisioning and the actual protected local channel remain unresolved implementation decisions, not permission to install either.

Two distinct interfaces are required:

1. **Pure structural comparison:** the independent expected input is a strict object containing `version: 1`, contractDigest, expectedPhase, binding, boundary, predecessorDigest, trustedRegistryRevision, revocationEpoch, and deadlines. expectedPhase uses the three phase enum values; binding/boundary use the same exact shapes above; predecessorDigest is nullable only for pre-exec. Deadlines contain bootId and safe nonnegative monotonic millisecond values startedAt, execBy, stopBy, observeBy and finalCleanupBy in that order, with startedAt < execBy and subsequent values nondecreasing. Registry revision is a bounded opaque identifier and revocationEpoch a safe nonnegative integer. Optional externally supplied comparison time is separately typed `{bootId, nowMonoMs}`; absence prevents time evaluation, and its presence remains a supplied assertion rather than a live clock observation. Expected input is not authenticated by being passed to a pure function. Independent expected contract/binding plus supplied JSON returns `contract_matches`, `mismatch` or `unknown`, bounded reason codes, and always `admission`, `settlement` and `import` equal to `not_evaluated`. Forgery may be structurally indistinguishable from a genuine record; a match explicitly makes no provenance claim.
2. **Future trusted authority verification:** consumer authenticates origin outside worker-controlled input, resolves immutable references, checks current registry/revocation, exact live binding, deadlines and current authority mechanism, then produces a private verification result bound to record digest and one intended phase. No such producer/consumer exists today. This result is only one prerequisite to a separate dispatch or settlement transaction, never a launch/import command.

## Phase, replay and expiry rules

Pre-exec identity and authority verification must finish while the registered operation fence is current, before the one-use payload grant. Its verified digest is included in the immutable operation launch record. A grant from another job, phase, generation, admitted source head, policy, boot or invocation is unusable. Snapshot/teardown must additionally bind the later candidate checkpoint; a null-to-candidate transition needs the store-owned association, not worker output or an unrestricted candidate rewrite. The protected grant consumer must atomically consume it; saving a JSON `consumed` flag is not sufficient.

At each phase require `issuedAt <= notBefore <= now < expiresAt`, the same boot, the current trust/revocation epoch and the exact phase record chain. Also require expiry no later than that phase's admitted absolute deadline: execBy for pre-exec, observeBy for snapshot and finalCleanupBy for teardown. Current process receipts use `Date.now()` wall-clock timestamps, not this monotonic timeline. The trusted observer must supply independently admitted boot-bound monotonic deadlines and observations, or an authenticated, bounded clock conversion tied to that boot and observation interval. Never compare old wall-clock receipt numbers directly with monotonic deadlines; missing/ambiguous conversion is UNKNOWN. Existing start/exec/stop/observe/final-cleanup deadlines never reset. Wall-clock correction, pause, restart and quota waits do not extend them. Unknown clock relation or inaccessible revocation information blocks fresh action.

Expiry prevents fresh authority use; it does not erase an immutable historical observation. A historical record can support later reconciliation only through a separately specified recovery policy with current provenance, exact durable seal, matching identities and no new execution. This contract grants no such recovery exemption. Duplicate delivery of identical evidence may be idempotently recognized, but never creates another grant, release, charge, refund or import. Same recordId with different bytes is a conflict.

The independent expected context must bind the predecessor phase and digest, issuer trust context, invariant operation/source/policy binding, boot, invocation and anchor. Snapshot follows pre_exec; teardown follows snapshot. Reject skipped, swapped, cross-operation or worker-selected predecessors. Candidate and inventory additions require the store-owned associations above, and teardown must preserve them exactly.

At snapshot, compare the actual durable operation seal under current store ownership; require closed launch gate, frozen domain and stable complete membership equal to the authenticated anchor. Its `populated=1` is expected, not an empty-group observation. Commit the workload-empty snapshot before teardown authorization. The outside observer then performs the selected manager-controlled thaw under the same pinned boot/unit/invocation/cgroup/anchor identity and remaining absolute deadline; record the transition and refuse an unknown or changed identity. The worker is already terminal, authority remains sealed, and the retained anchor is the only live member. Only after confirmed thaw may the one-use teardown grant let the anchor proceed. Missing/interrupted thaw remains UNKNOWN; no alternate signal or direct-cgroup fallback is authorized. Teardown may only finalize existing evidence and exit, with no new children or helpers. Any externalized work, unexpected member, early prune, lost observer, ambiguous transition or unproven peer protection retains UNKNOWN and the fence.

## Implementation admission and effort

**Preparation result:** interface, producer ownership, binding/expiry and negative cases are specified. A pure companion implementation is narrowly specifiable, but the complete authority route is unsupported by the current adapter and cannot be declared implementation-ready for runtime integration.

If separately selected, the pure slice would own a new `src/settlement-authority-contract.mjs`, its focused `test/settlement-authority-contract.test.mjs`, and this document. Preserve v1 comparator/store/runtime behavior; add no process calls, trust registry, permission changes or dispatch/import consumer. Independent review must verify literal bounds, non-mutation, independent expected binding, phase distinctions and absence of an admitting return. Merely implementing more supplied-metadata comparison does not resolve the runtime blocker.

Full remaining estimates are engineering judgment, not measured throughput: pure slice 1–2 active engineering days including review/docs/ordinary CI; actual provider/barrier/credential and policy transport 2–4 days, observer/anchor/deadlines 1–2, store/restart/import 1–2, independent fault validation/review/CI 1–2, totaling 5–10 additional days if a supported authority mechanism already exists. Provisioning, new privilege design and native acceptance authorization are excluded and may dominate. The next owner decision is selecting an already supported protected transition/channel mechanism, or authorizing a separately scoped design for one; no automatic new daemon/identity/security configuration follows.

- [Systemd v259 resource control](https://raw.githubusercontent.com/systemd/systemd/v259/man/systemd.resource-control.xml): delegation semantics.
- [Systemd v259 execution](https://raw.githubusercontent.com/systemd/systemd/v259/man/systemd.exec.xml): user/group and execution-context settings; these do not automatically create an anchor/child privilege split.
- [Systemd v259 manager API](https://raw.githubusercontent.com/systemd/systemd/v259/man/org.freedesktop.systemd1.xml): transient-unit/control API and authorization boundary.
