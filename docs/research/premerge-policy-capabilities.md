# Premerge policy capability boundaries

This page describes the GitHub delivery adapter's source-defined preflight and inspection behavior. Source snapshot: `50cbf10580670be193d6035763e4c2b9a1a497fa`. This documentation-only adaptation is recorded against repository baseline `8e410c01b58d99ce6934ff80af0cb98993d9c8b0`.

A successful source-defined preflight means the configured policy checks passed against the metadata returned by that preflight. It does not establish that every server rule is automated or that a particular repository is eligible to merge. The adapter reports unsupported or uncertain conditions as blocked or pending; it does not relax policy to proceed.

| Configuration or observation | Adapter behavior | Capability boundary |
| --- | --- | --- |
| Repository and classic branch protection | [Preflight](../../src/delivery.mjs#L57-L72) requires an active repository, push permission, readable classic branch protection, strict status checks, and administrator enforcement. Failure to read branch protection blocks with `github_policy`. | Missing, denied, or unsupported metadata blocks. Ruleset-only protection cannot substitute for the required classic branch-protection response. |
| Configured check name and app | For each configured requirement, protection must include the exact check name. A server app ID that is null or absent is accepted; otherwise it must equal the configured app ID. Legacy `contexts` are used only when `checks` is null or absent. If `checks` is an empty array, that array is used and the legacy contexts are not consulted. [Observed check selection](../../src/delivery.mjs#L116-L124) still requires the exact configured name, app ID, and evidence SHA. | A missing server-side app binding is accepted during the protection comparison, but a check run still has to match the configured app ID and evidence SHA. Server omission does not make observed check runs interchangeable. |
| Explicit any-app server ID | GitHub documents `app_id: -1` as any app. When the configured app ID is positive, the adapter's protection comparison accepts only a null/absent server app ID or an exact ID match; `-1` therefore does not match. | This adapter is narrower than the documented any-app setting. |
| Additional server requirements | Preflight iterates the configured requirements; it does not require the complete server requirement set to be identical. Active rules other than `merge_queue` do not receive a per-rule automation check here. | Passing the configured subset does not establish that extra reviews, signatures, conversation resolution, or other checks are satisfied. Server enforcement may still reject a merge. |
| Merge methods and queue | Preflight checks permission for the configured squash or merge method, reads branch rules, and blocks if the rules response is not an array or includes a `merge_queue` rule. | The adapter has no queue-driving path or established rebase-merge route. It does not fall back to another merge method. |
| Candidate and synthetic merge observations | [Inspection](../../src/delivery.mjs#L103-L128) verifies the synthetic merge commit's tree and ordered parents when its check-run response is nonempty. For each configured check, a matching synthetic-commit observation takes precedence; candidate-commit observations are considered if no matching synthetic observation exists. Matching runs are sorted by descending numeric ID, and the selected run must be completed and successful. | Selection is limited to the returned API response set; it does not establish that arbitrary unseen or historical runs were considered. Missing runs remain pending. Failure, skipped, and neutral conclusions do not pass. A run with the wrong app or head SHA cannot satisfy the local requirement. |
| Pagination and uncertain mergeability | The [client](../../src/delivery.mjs#L6-L27) requests 100 entries per page for up to 20 pages, requires a short page to end pagination normally, and throws when the bound is exhausted. Inspection remains pending when mergeability is null or its state is `unknown`, and blocks a reported conflict. | Pagination limits and uncertainty are not treated as complete success. Preflight and inspection observe remote metadata before later effects; they do not freeze remote policy or state atomically. |

## Public API references

The [branch-protection REST reference](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection) describes strict checks, administrator enforcement, and app binding, including the any-app value. The adapter behavior above records which of those configurations its source accepts.

The [branch-rules endpoint](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch) describes applicable active rules across repository and organization levels and excludes evaluate-only or disabled rulesets. Its `merge_queue` rule requires queue-based merging; the adapter refuses that rule because it has no queue-driving path.

The [check-runs reference](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference) documents a default latest filter. The source client does not set `filter=all`, so descending-ID selection applies only within the returned response set; it is not an inventory of every historical check run. The client pins API version `2022-11-28`. These public references were checked on 17 October 2026; this page does not establish documentation or live-response equivalence across API versions.

## Fixture scope

The [protection and queue fixtures](../../test/delivery.test.mjs#L35-L38) and [paged rerun matrix](../../test/delivery-evidence-matrix.test.mjs#L91-L103) define test scenarios. Their definitions are not evidence that a test was executed or that a live repository is ready. They do not cover all additional server policies.

Proposed negative cases, not executed evidence, include explicit any-app protection, an empty `checks` array alongside legacy contexts, extra server requirements, pagination exhaustion, and metadata changing between observation and mutation.

This page describes adapter capability boundaries. It does not establish current policy eligibility, CI success, acceptance by a hosting service, or runtime readiness for a particular repository.
