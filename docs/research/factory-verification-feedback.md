# Bounded verification failure feedback

Research date: 15 October 2026. Baseline source snapshot: [`fe87da7`](https://github.com/Zkrausman/Squire/commit/fe87da73798d327ac3557d2d245146c6dd12ef3f). This is a narrow refinement of the existing T1 bounded repair-diagnostic projection, reused by T3's correction export in the [trust and privacy design](factory-trust-boundaries.md). The implementation status below is local to this source checkout; it is not evidence of a reproduced defect, merged release, or live-model outcome.

## Decision

Implement one stream-separated, byte-bounded projection for failed verification feedback. The baseline formatter joins standard output, a newline, and standard error, then keeps the final 6,000 JavaScript string code units. That can omit an early assertion or compiler error; a long standard-error stream can also displace all standard output. The bounded head-and-tail projection makes early and final diagnostics available from each explicitly classified stream within an exact serialized-payload bound.

This is a static information-loss finding, not a measured incident rate or a claim that repairs currently fail. Retained command logs and candidate evidence already preserve useful source material. The narrow implementation now concerns the bounded text sent into automatic repair and explicitly admitted correction; it does not add a receipt reader, evidence store, replay mechanism, status surface, or new repair authority.

This source check is supplemental to the older pins in the cumulative roadmap and trust memo. The feedback gap is distinct from delivered terminal status, A3 declared inputs, bounded receipt reading/boundaries, and passive inspect-delivery work in PRs 133–138. It refines the existing T1/T3 ownership to expose approved diagnostics already present in check results.

The refinement stays inside the existing T1/T3 work. It does not reorder the roadmap's committed owner outcomes: recovery, then preflight, then an accepted delivery. No research-based efficiency or savings claim supports moving it ahead of that order.

## Research context and limits

Fan et al., [*An Empirical Study of Harness Design for Coding Agents*](https://arxiv.org/html/2609.20804v1) (v1, checked 15 October 2026), discusses tool-result limits and studies staged elision and summarization policies in Sections 2.3 and 3.1–3.2. It motivates examining bounded feedback, but does not isolate Squire's 6,000-code-unit suffix, separate-stream head-and-tail allocation, or the formatter implemented here. Its reported efficiency effects do not estimate Squire outcomes, savings, or call reduction; its limitations include one run per task and bundled interventions. It supplies no authority to remove checks, change models, add summarizer calls, or run a comparison.

The [Node 24 `Buffer.byteLength` documentation](https://nodejs.org/docs/latest-v24.x/api/buffer.html#static-method-bufferbytelengthstring-encoding), checked 15 October 2026, supports measuring UTF-8 bytes rather than treating JavaScript string length as a byte bound. It does not supply a diagnostic selection rule or guarantee token counts, confidentiality, or model effectiveness. Pin and validate the actual supported Node 24 version during any separately authorized implementation.

## Implemented narrow contract

- Format only the already admitted in-memory check result. Do not open receipt-supplied paths, raise process output limits, or change canonical raw evidence, candidate binding, or operation identity.
- Keep standard output and standard error separate and labeled. For each approved stream, retain an initial and final segment within one fixed total 8,192-byte serialized diagnostic payload for a handoff. The cap covers all entries, labels, metadata, and JSON escaping; it is not multiplied per record. A short stream fits intact and deterministic unused allowance is redistributed. Do not treat the old 6,000 code units as a byte limit.
- Measure shown and omitted UTF-8 bytes from the decoded stream strings available to the formatter. Preserve Unicode scalar values at clipping boundaries, including supplementary characters; do not duplicate overlapping head and tail segments. Since process output has already been decoded, this does not reconstruct the original bytes when invalid UTF-8 was replaced upstream.
- Include shown/omitted UTF-8 byte counts and capture-incomplete flags only when that check's metadata classification is approved. Do not expose lengths for withheld streams. Count only decoded text available after filtering; never infer total child-emitted bytes. Unicode scalar boundaries are preserved; invalid surrogate code units are replaced before clipping.
- A strict, optional `diagnosticDisclosureV1` check field classifies `stdout`, `stderr`, and `metadata` as `approved` or `withheld`; omitted categories default to withheld without mutating configuration. The field is accepted only for configured service checks. Classification is not destination authorization. If both streams are withheld, the provider receives only one fixed withheld indication, regardless of metadata classification. No real configured check is opted in by this slice.
- Frame the excerpt as untrusted diagnostic data. A head-and-tail formatter is not redaction, private-grader isolation, prompt-injection protection, or a way to grant authority. Do not add raw absolute paths, arbitrary reader handles, or automatic recall authority.
- Keep exit, timeout, stop, launch, output-limit, check ordering, and not-run facts independent of the excerpt. A pass result adds no diagnostic. Formatter failure reports unavailable feedback while preserving the original verification outcome and candidate identity; it does not reserve a call or trigger a retry. Diagnostic text never becomes argv or policy.
- Use one versioned `diagnosticFeedbackV1` projection for candidate-bound automatic repair and explicitly admitted correction. Preserve historical `failureTail` values and receipts locally. New prompt consumers revalidate its candidate and policy binding and never fall back to raw legacy text; an absent, malformed, stale, or old projection is withheld. Avoid serializing duplicate old and new diagnostics. Do not rewrite historical state or accepted schemas.

**Remaining effort:** inspect the final source diff and use the existing ordinary CI/review/publication route. The implementation adds strict classification validation, clipped shared projection, prompt-boundary binding checks, and an isolated synthetic suite. Broader T1 environment-profile work and T3 publication-policy work remain separate obligations; this refinement does not complete either ticket.

**Dependencies:** existing process/check result facts; per-check/per-stream classification for the already admitted repair runtime; compatibility with correction admission and retained evidence. This change does not authorize any new destination or runtime. R1–R6 completion and a benchmark baseline are not dependencies for this bounded projection. An immutable reference, if later needed, should reuse R3/A2 identity; a new artifact reader is outside this slice.

**Remaining limits:** the per-check classifications identify permitted data classes only. They do not authorize provider destinations, unfiltered/private-grader output, owner-status export, raw-reader recall, public GitHub disclosure, or arbitrary metadata. No host capability probe, live provider call, model download, held benchmark, or Herdr/Gelt/Pith work is part of this slice.

**Focused synthetic fixture coverage:**

The isolated direct suite covers strict schema scope, default/metadata-only withholding, separate approved and excluded streams, aggregate serialized cap, Unicode and JSON escaping, candidate/policy mismatch, legacy raw-reason sanitization, pass shape, and fake-runner integration. These deterministic tests establish only the named behavior; they cannot prove arbitrary secret absence or model immunity. The existing `test/verification.test.mjs` mixed integration remains CI-only and was not used as the local inert route.

## Runner-up, assumption, and stop condition

The runner-up is further failed-output retention or recall integration under R3/A2. It may improve provenance, but it adds reader, identity, and export compatibility already partly covered by recent delivery work and does not address the current repair-text bottleneck as directly. Reuse delivered evidence facilities; do not create another reader in this slice.

The decisive assumption is that bounded, explicitly classified diagnostics are useful to the already admitted repair runtime. Source establishes the lossy projection; it does not establish how often this matters. If no stream is classified approved, the fixed withheld outcome is expected. Preserve the execution holds and committed roadmap order; this narrow implementation does not establish safety for arbitrary output or complete T1/T3 delivery.
